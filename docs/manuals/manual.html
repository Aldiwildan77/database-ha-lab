1. What the lab is

A research and benchmarking lab for database high availability. Ansible installs a database engine directly on your servers (no containers), builds one HA topology on top, and gives you commands to switch over, fail over, inject faults, recover and benchmark. Prometheus, Grafana and JMeter run on your own machine (the operator machine).

PartWhere it runsWhat it does
Ansible playbooks + engine descriptorsoperator machineProvision, deploy HA, switchover, failover, recover, destroy
Database server (lab port)every nodeMySQL, MariaDB or PostgreSQL on a non-standard port
Exporters + lab collectorevery nodenode_exporter, engine exporter, HA collector
Prometheus + Grafana + probeoperator machine (Docker)Metrics, eight dashboards, client-side latency probe
JMeteroperator machineLoad scenarios through the HA endpoint or one node

One lab runs one engine and one HA strategy at a time, chosen in config/ha.yml (db_engine, ha_provider).

3. Preparing the nodes

3.1 Choosing servers

  • Bare metal or VMs both work. Cloud VMs, Proxmox/VMware VMs and local VMs (UTM, VirtualBox) are fine if the operator machine reaches them.
  • MySQL needs x86_64. repo.mysql.com publishes amd64 packages only. On Apple-silicon UTM (arm64) use MariaDB or PostgreSQL.
  • Servers that already run other services are supported. The lab uses its own ports and refuses to touch anything it did not create (chapter 11).

3.2 SSH key

ssh-keygen -t ed25519 -f ~/.ssh/db-ha-lab_ed25519 -C "db-ha-lab"
ssh-copy-id -i ~/.ssh/db-ha-lab_ed25519.pub <user>@<node>
ssh-add --apple-use-keychain ~/.ssh/db-ha-lab_ed25519     # macOS: key with a passphrase

Ed25519 is the recommended key type: short, fast and as strong as RSA-3072+. The -C comment is a label only; it does not bind the key to an email account.

3.3 A user with passwordless sudo

Each node can use a different SSH user (set per node in inventory.yml). To create a dedicated user, run once on each node as an existing sudo user:

KEY="ssh-ed25519 AAAA... db-ha-lab"
sudo useradd -m -s /bin/bash db-ha-lab
sudo install -d -m 700 -o db-ha-lab -g db-ha-lab /home/db-ha-lab/.ssh
echo "$KEY" | sudo tee /home/db-ha-lab/.ssh/authorized_keys >/dev/null
sudo chown db-ha-lab: /home/db-ha-lab/.ssh/authorized_keys; sudo chmod 600 /home/db-ha-lab/.ssh/authorized_keys
echo "db-ha-lab ALL=(ALL) NOPASSWD:ALL" | sudo tee /etc/sudoers.d/db-ha-lab >/dev/null
sudo chmod 440 /etc/sudoers.d/db-ha-lab && sudo visudo -cf /etc/sudoers.d/db-ha-lab
Why NOPASSWD sudoAnsible runs many privileged steps non-interactively. Without it, every run needs ARGS=-K and the password. The user does not need to be root, and root login over SSH is not needed.

3.4 Before the first run

  • No other apt may be running. A forgotten interactive apt install holds the dpkg lock for hours (see 12.1).
  • On Ubuntu, stop needrestart from waiting for an answer: 
    echo "\$nrconf{restart} = 'a';" | sudo tee /etc/needrestart/conf.d/50-auto.conf
  • python3 must be installed (Ubuntu and Debian ship it).

4.4 WireGuard overlay between two servers (case 5)

Use it when nodes cannot reach each other directly, for example when one tailnet device is tagged and cannot reach machines shared into the tailnet. One side listens; the other connects over a path that already works (here, Tailscale).

# both servers
sudo apt-get install -y wireguard
sudo sh -c 'umask 077; wg genkey > /etc/wireguard/lab.key'
sudo cat /etc/wireguard/lab.key | wg pubkey            # note the public key

# server A (listens) /etc/wireguard/wg-lab.conf
[Interface]
Address = 10.99.0.1/24
ListenPort = 51820
PostUp = wg set %i private-key /etc/wireguard/lab.key
[Peer]
PublicKey = <B public key>
AllowedIPs = 10.99.0.2/32

# server B (connects) /etc/wireguard/wg-lab.conf
[Interface]
Address = 10.99.0.2/24
PostUp = wg set %i private-key /etc/wireguard/lab.key
[Peer]
PublicKey = <A public key>
Endpoint = <A reachable IP>:51820
AllowedIPs = 10.99.0.1/32
PersistentKeepalive = 25

# both
sudo systemctl enable --now wg-quick@wg-lab
sudo wg show            # "latest handshake" must be recent
ping -c3 10.99.0.1      # from B

Inventory for this layout:

environment: {name: lab, network: wg, operator_network: tailnet}
networks:
  wg:      {type: vpn, interface: wg-lab, cidrs: [10.99.0.0/24]}
  tailnet: {type: tailscale}
nodes:
  - name: lab-a
    addresses: {wg: 10.99.0.1, tailnet: 100.x.y.z}
    role: primary
    datacenter: dc-01
    ssh: {user: lab1, private_key: ~/.ssh/db-ha-lab_ed25519}
Effect on the existing serverWireGuard adds one interface and one route (10.99.0.0/24). It does not change the default route, DNS, Docker networks or firewall rules. Pick a subnet that does not overlap existing routes (ip route, docker network inspect). Remove with sudo systemctl disable --now wg-quick@wg-lab.

4.5 Firewall

  • Default backend nftables: the lab loads its own table inet halab (halab-firewall.service). It covers only the lab ports. On the node-network and operator-network interfaces it accepts the networks' cidrs plus allowed_sources and drops other sources for those ports. Other ports and existing rules are untouched.
  • ufw already active on the host: ufw drops in its own table whatever halab accepts. The lab therefore also adds narrow ufw allow rules (comment ha-lab): lab ports only, from lab sources only, on lab interfaces only. ufw's policy and your rules are not changed. make destroy DATA=1 removes them.
  • firewall.backend: ufw in config/monitoring.yml makes ufw the backend (host-wide default deny). none leaves the firewall to you.
Docker and ufwPorts published by Docker (0.0.0.0:6379->6379) skip ufw rules. Lab rules do not change that. Bind published ports to 127.0.0.1 or a private address if the server is public.

Switching strategy or engine: follow this order make destroy acts on what config/ha.yml says now. Run it before you edit the file.

    • Same engine, other strategy: make destroy
    • Other engine: make destroy DATA=1 (deletes the database packages and all data)
  2. Edit ha_provider (and db_engine) in config/ha.yml.
  3. If db_engine changed, run make provision.
  4. Run make ha.
Deployment refuses a different provider while the old one is still recorded on the nodes.
make ha and HA=make ha deploys ha_provider from config/ha.yml. make ha HA=x is accepted only when x equals that value.

7.1 Per-strategy notes

MySQL async-replication / semi-sync

  • GTID with SOURCE_AUTO_POSITION=1; replicas are super_read_only.
  • repl account exists on every node, created with sql_log_bin=0, so any node can be promoted without errant GTIDs.
  • Semi-sync settings (config/ha.yml → semi_sync): wait_for_replica_count (1), timeout_ms (10000), wait_point (AFTER_SYNC).

MySQL orchestrator

  • Percona Orchestrator on every node with raft (no backend DB). HTTP on 13000, basic auth orchestrator / db_admin_password.
  • Decides who is primary; it cannot recover transactions that never left the failed primary.

MySQL innodb-cluster

  • Single-primary Group Replication managed with MySQL Shell. MySQL Router on every node: RW 16446, RO 16447.

MySQL percona-xtradb-cluster

  • Replaces Oracle MySQL packages: choose it before provisioning. pxc_strict_mode=ENFORCING, SST xtrabackup-v2.

MariaDB galera

  • galera-4, SST mariabackup, TLS forced on private networks.
  • make recover handles one node down, quorum loss, and full outage (bootstraps from the highest seqno; override with -e mariadb_galera_bootstrap_node=<node>).

PostgreSQL streaming / sync-replication

  • One PGDG cluster named halab per node; other clusters are never touched.
  • Standbys built by pg_basebackup; wal_log_hints=on so an old primary can be rewound. wal_keep_size=1GB, no slots.
  • Rewind needs db_admin_password.

PostgreSQL patroni

  • Per node: halab-etcd, halab-patroni (REST 18008, TLS), PostgreSQL 15432. etcd client 12379, peer 12380.
  • Switchover via Patroni REST /switchover. Automatic failover when the leader key expires (~30 s).

Full runbooks: ha/<engine>/<strategy>/README.md.

8. Test scenarios

8.1 Planned switchover

make switchover                         # picks the most advanced candidate
make switchover NEW_PRIMARY=lab-ivan

Fences the old primary, waits for the candidate to catch up, promotes it, repoints the others. If promotion fails, the old primary is unfenced. Expected data loss: none.

8.2 Unplanned failover (primary lost)

make fault NODE=lab-hanif FAULT=kill-db CONFIRM=yes
make topology
make promote                           # or NEW_PRIMARY=lab-ivan; FORCE=1 skips safety checks
make recover NODE=lab-hanif            # old primary rejoins as replica

Manual strategies need make promote. Automatic strategies (orchestrator, innodb-cluster, patroni) promote by themselves; Galera/PXC have no promotion.

11. Safety guarantees

  • Existing services are protected. make plan-host is read-only and runs before provisioning. Provisioning stops if a lab port is in use, a conflicting database package is installed, or (MySQL) the buffer pool would not fit in free memory.
  • Packages never grab default ports. The lab port config is written before the server package is installed, so the package's first start does not bind 3306 next to an existing server.
  • Existing data is protected. The lab refuses a datadir or cluster it did not create. It marks its own with .ha-lab-managed before installing, so a failed run can be resumed. Take over an existing server only with ARGS="-e mysql_adopt_existing=true" (or mariadb_, postgres_); data is never deleted.
  • Repositories are pinned to each engine's own packages.
  • Time sync: an existing ntp/ntpsec/openntpd is kept; chrony only when none exists.
  • Topology switches are explicit (chapter 6).
  • No divergent replicas. Errant GTIDs are refused; PostgreSQL never replaces a replica's data unless -e postgres_rebuild_replica=true.
  • Faults need CONFIRM=yes; isolate and netem schedule their own restore.
  • make destroy asks for the environment name; DATA=1 also purges packages and data.
  • Secrets stay out of Git. Real config files, secrets and generated targets are gitignored.
  • No database root password is managed: Ansible uses the local socket (auth_socket / peer auth).
